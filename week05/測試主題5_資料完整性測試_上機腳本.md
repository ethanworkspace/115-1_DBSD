## 這一節在做什麼，以及為什麼要做

本課程主軸是 AI 時代的軟體測試與驗證。人工智慧 artificial intelligence（AI）工具可以在三秒內
產生一段建表語法 Data Definition Language（DDL），語法也會通過，但「約束到底有沒有生效」
不會寫在它的回答裡。唯一的確認方式是故意做壞事，看資料庫擋不擋。

這一節的做法是：每一項都先寫下你預期資料庫會拒絕，再真的送出去，然後把畫面上的錯誤訊息抄下來。
資料庫把你擋下來，就是約束在替你工作的證據；資料庫收下了，代表那條約束當初沒有建起來，
你手上這張表其實沒有你以為的保護。

**重要觀念**：測試成功的定義在這一節是反過來的。看到紅色錯誤訊息＝通過；順利寫進去＝不通過。

## 做之前先備份，兩句，30 秒

```sql
CREATE TABLE ships_backup AS SELECT * FROM ships;
SELECT COUNT(*) FROM ships_backup;
```

第二句必須回 **50**。三個版本的「我的 50 筆」都是 50 列，這個數字和你的版本無關。
後面每做完一項，都可以用 `SELECT COUNT(*) FROM ships;` 確認仍然是 50。

## 步驟 0　先看清楚你手上的表是什麼，3 分鐘

第 4 週是用 phpMyAdmin 的匯入功能把逗號分隔值 comma-separated values（CSV）檔讀進來的。
匯入精靈只負責把資料搬進去，不會替你設主鍵 primary key（PK），也不一定用支援外鍵的儲存引擎。
所以先查，不要假設。

```sql
SELECT VERSION();
SELECT @@sql_mode;
SHOW CREATE TABLE ships;
```

三句各看一件事：第一句是資料庫版本，錯誤訊息的文字會隨版本不同；第二句是嚴格模式
strict mode 有沒有開，字串裡要找得到 `STRICT_TRANS_TABLES`；第三句最重要，看最後一行的
`ENGINE=` 是什麼，以及有沒有 `PRIMARY KEY (ship_id)` 這一行。

如果沒有主鍵或引擎不是 InnoDB，依序補上。每一句送出後都看一次結果再送下一句。

```sql
ALTER TABLE ships ENGINE = InnoDB;
ALTER TABLE ships MODIFY ship_id INT NOT NULL;
ALTER TABLE ships ADD PRIMARY KEY (ship_id);
ALTER TABLE ships MODIFY `船型` VARCHAR(10) NOT NULL;
ALTER TABLE ships MODIFY `噸位_千噸` DOUBLE NOT NULL;
ALTER TABLE ships MODIFY `靠泊時間_小時` DOUBLE NOT NULL;
```

| 這一步出現的訊息 | 代表什麼 | 怎麼辦 |
|---|---|---|
| `#1068 - Multiple primary key defined` | 第 4 週匯入時主鍵已經設好了 | 跳過這一句，其餘照做 |
| `#1062 - Duplicate entry ... for key 'PRIMARY'` 出現在 ADD PRIMARY KEY | 你的 50 列裡有重複的 ship_id，資料本身就壞了 | 先跑步驟 6 的自我檢查找出重複那一筆，修掉再回來 |
| `#1138 - Invalid use of NULL value` 出現在 MODIFY NOT NULL | 有欄位是空的，匯入時掉了格 | 同上，先修資料 |
| 六句都成功 | 你的 50 筆乾淨，而且約束現在真的存在 | 往下做 |

三個版本的原始資料我都實際查過：四個欄位各 0 筆 NULL、ship_id 從 1 到 50 共 50 個相異值、
船型只有貨櫃、散裝、油輪三種、噸位與靠泊時間都沒有小於等於 0 的值。所以六句正常情況下會全部成功；
會失敗就表示你的匯入出了事，那本身就是這一節要抓的東西。

## 測試一　重複主鍵，2 分鐘

ship_id = 1 在三個版本裡都存在，所以下面這句一定是重複。

```sql
INSERT INTO ships (ship_id, `船型`, `噸位_千噸`, `靠泊時間_小時`)
VALUES (1, '貨櫃', 99.9, 25.0);
```

| 項目 | 內容 |
|---|---|
| 預期訊息 | `#1062 - Duplicate entry '1' for key 'PRIMARY'`。MySQL 8 會寫成 `for key 'ships.PRIMARY'`，意思相同 |
| 證明了什麼 | 主鍵約束在起作用。主鍵的兩個條件是不重複與不為空，這一句踩的是第一個 |
| 沒擋下來代表什麼 | ships 根本沒有主鍵，只是一堆看起來有編號的列。你的表現在有兩筆 ship_id = 1，之後任何用 ship_id 查單一艘船的語句都會回兩列，而 JOIN 會把筆數翻倍 |
| 沒擋下來怎麼辦 | 用 ``DELETE FROM ships WHERE ship_id = 1 AND `噸位_千噸` = 99.9;`` 刪掉剛剛那筆，回步驟 0 補 `ADD PRIMARY KEY`，再重測一次 |

## 測試二　NOT NULL 塞空值，2 分鐘

非空約束 NOT NULL 有兩種踩法，兩種的錯誤號碼不一樣，兩句都要跑。

```sql
INSERT INTO ships (ship_id, `船型`, `噸位_千噸`, `靠泊時間_小時`)
VALUES (101, NULL, 50.0, 20.0);

INSERT INTO ships (ship_id, `噸位_千噸`, `靠泊時間_小時`)
VALUES (102, 50.0, 20.0);
```

| 項目 | 內容 |
|---|---|
| 預期訊息 | 第一句 `#1048 - Column '船型' cannot be null`，這是明寫 NULL；第二句 `#1364 - Field '船型' doesn't have a default value`，這是整欄不給值 |
| 證明了什麼 | 非空約束在起作用，而且它擋的是「這一格沒有值」，不是「這一格的值不合理」 |
| 沒擋下來代表什麼 | 兩種結果都要分辨。若第一句成功，該欄允許 NULL，你的表裡會出現沒有船型的船；若第二句成功而該欄被自動填成空字串或 0，表示嚴格模式沒開，資料庫在替你猜值 |
| 沒擋下來怎麼辦 | `DELETE FROM ships WHERE ship_id IN (101, 102);`，然後回步驟 0 跑 `MODIFY ... NOT NULL`，並記下 `@@sql_mode` 裡有沒有 `STRICT_TRANS_TABLES` |

補一句提醒：NULL 不等於 0，也不等於空字串。NULL 的意思是「不知道」。這個差別下一節用
`COUNT(*)` 與 `COUNT(欄位)` 就會看到，兩者在有 NULL 的時候給出不同答案。

## 測試三　型別不符，把文字塞進數值欄，3 分鐘

```sql
INSERT INTO ships (ship_id, `船型`, `噸位_千噸`, `靠泊時間_小時`)
VALUES (103, '貨櫃', '很重', 20.0);

INSERT INTO ships (ship_id, `船型`, `噸位_千噸`, `靠泊時間_小時`)
VALUES (104, '貨櫃', '20.5公噸', 20.0);
```

| 項目 | 內容 |
|---|---|
| 預期訊息 | 第一句在 MariaDB 會是 `#1366 - Incorrect DOUBLE value: '很重' for column ... at row 1`，MySQL 8 可能顯示 `#1265 - Data truncated for column '噸位_千噸' at row 1`。文字依版本不同，兩種都算擋下來 |
| 證明了什麼 | 型別約束在起作用。欄位宣告成 DOUBLE，資料庫就負責保證這一欄裡每一格都是數字，而不是等到你算平均時才爆掉 |
| 沒擋下來代表什麼 | 這是今天最需要分辨的一項。如果畫面寫 **1 row affected, 1 warning**，那就是沒擋下來，嚴格模式是關的。第一句的「很重」會被收成 0，第二句的「20.5公噸」會被切成 20.5。你的平均噸位從此是錯的，而且錯得安靜，沒有任何紅字 |
| 沒擋下來怎麼辦 | 先 `SHOW WARNINGS;` 看它到底做了什麼，再用 ``SELECT ship_id, `噸位_千噸` FROM ships WHERE ship_id IN (103, 104);`` 看實際存進去的值，然後 `DELETE FROM ships WHERE ship_id IN (103, 104);`。把 `@@sql_mode` 的內容抄進記錄表，這就是「同一句 SQL 在兩台電腦上結果不同」的實例 |

第二句比第一句重要。完全不是數字的「很重」任何設定都容易發現，但「20.5公噸」只是多了兩個字，
被切掉單位之後看起來完全正常。真實世界的壞資料長的就是第二句這樣。

## 測試四　不存在的外鍵，含建表共 10 分鐘

這門課到目前只有 ships 一張表，而外鍵 foreign key（FK）描述的是兩張表之間的關係，
所以要先有第二張表。voyages 代表每一次靠泊紀錄，一艘船可以有多次靠泊，是一對多。

**4-1　建表，1 分 30 秒**

```sql
CREATE TABLE voyages (
  voyage_id INT PRIMARY KEY,
  ship_id   INT NOT NULL,
  `港口`    VARCHAR(20) NOT NULL,
  FOREIGN KEY (ship_id) REFERENCES ships(ship_id)
) ENGINE = InnoDB;
```

建表就失敗的話，問題在 ships 不在 voyages。MariaDB 會回
`#1005 - Can't create table ... (errno: 150 "Foreign key constraint is incorrectly formed")`，
MySQL 會回 `#1215 - Cannot add foreign key constraint` 或 `#3780`。三個原因之一：ships 不是
InnoDB、ships 的 ship_id 沒有主鍵或索引、兩邊的 ship_id 型別不一致。回步驟 0 補完再回來。

**4-2　先放兩筆合法的，1 分 30 秒**

```sql
INSERT INTO voyages VALUES (1, 1, '高雄'), (2, 2, '台中');
SELECT COUNT(*) FROM voyages;
```

第二句必須回 **2**。ship_id 的 1 與 2 在三個版本裡都存在，所以這兩筆一定會成功。
先證明合法資料進得去，再去踩違規，否則等一下失敗了你分不出是約束擋的還是語法打錯。

**4-3　再放一筆指向不存在的船，2 分鐘**

ship_id = 999 在三個版本裡都不存在，我逐版查過，51、77、999 三個值的命中數都是 0。

```sql
INSERT INTO voyages VALUES (3, 999, '基隆');
```

| 項目 | 內容 |
|---|---|
| 預期訊息 | #1452 - Cannot add or update a child row: a foreign key constraint fails，括號裡會印出你的資料庫名、voyages、約束名 voyages_ibfk_1，以及 FOREIGN KEY (ship_id) REFERENCES ships (ship_id) |
| 證明了什麼 | 外鍵約束在起作用。它保證 voyages 的每一筆靠泊紀錄都掛在一艘真的存在的船上，也就是沒有孤兒資料 |
| 沒擋下來代表什麼 | 外鍵沒有真的建起來，最常見的原因是其中一張表是 MyISAM 引擎。MyISAM 會把 `FOREIGN KEY` 這段語法讀完、不報錯、然後完全忽略它。語法看起來有寫，行為上根本不存在，這是整個資料庫課裡最容易被 AI 產出的建表語法騙過去的一點 |
| 沒擋下來怎麼辦 | 跑 `SHOW CREATE TABLE voyages;` 看 CONSTRAINT 那一行還在不在，再跑 `SELECT ENGINE FROM information_schema.TABLES WHERE TABLE_NAME = 'voyages';`。確認是引擎問題就 `ALTER TABLE voyages ENGINE = InnoDB;` 後重建外鍵 |

**4-4　反方向再踩一次，刪掉被參照的那艘船，2 分鐘**

```sql
DELETE FROM ships WHERE ship_id = 1;
```

| 項目 | 內容 |
|---|---|
| 預期訊息 | `#1451 - Cannot delete or update a parent row: a foreign key constraint fails (...)` |
| 證明了什麼 | 外鍵是雙向保護。它不只擋你新增孤兒，也擋你製造孤兒。voyages 第 1 筆指著 ship_id = 1，這艘船就不能被刪掉 |
| 沒擋下來代表什麼 | 你的 ships 從 50 筆變成 49 筆，而 voyages 第 1 筆變成指向不存在的船。這是最危險的一種，因為刪除成功時畫面是綠色的，沒有任何東西提醒你剛剛弄壞了一張表 |
| 沒擋下來怎麼辦 | 馬上從備份補回來：`INSERT INTO ships SELECT * FROM ships_backup WHERE ship_id = 1;` 然後 `SELECT COUNT(*) FROM ships;` 確認回到 50 |

## 步驟 5　孤兒資料自我檢查：把測試寫成可判定的形式，4 分鐘

前面四項是「送出違規、看它擋不擋」，靠的是人看錯誤訊息。但人會看漏，而且下週、下學期、
交接給別人的時候沒有人會重看一遍。所以要把同樣的規則寫成查詢：**答案是 0 就通過，不是 0 就不通過**。
這就是這門課說的「規格變成驗收條件」，不需要任何人判斷語氣。

```sql
-- 檢查 1　孤兒資料：有靠泊紀錄掛在不存在的船上嗎
SELECT COUNT(*) AS 孤兒筆數
FROM voyages v LEFT JOIN ships s ON v.ship_id = s.ship_id
WHERE s.ship_id IS NULL;

-- 檢查 2　主鍵重複：有幾個 ship_id 出現超過一次
SELECT COUNT(*) AS 重複的編號個數
FROM (SELECT ship_id FROM ships GROUP BY ship_id HAVING COUNT(*) > 1) AS t;

-- 檢查 3　空值：四個欄位有任何一格是空的嗎
SELECT COUNT(*) AS 有空格的筆數 FROM ships
WHERE ship_id IS NULL OR `船型` IS NULL
   OR `噸位_千噸` IS NULL OR `靠泊時間_小時` IS NULL;

-- 檢查 4　值域：船型只能是這三種，噸位與靠泊時間必須大於 0
SELECT COUNT(*) AS 不合規筆數 FROM ships
WHERE `船型` NOT IN ('貨櫃', '散裝', '油輪')
   OR `噸位_千噸` <= 0 OR `靠泊時間_小時` <= 0;

-- 檢查 5　看不見的字元：船型有沒有前後空白，是不是剛好兩個字
SELECT COUNT(*) AS 字元有問題的筆數 FROM ships
WHERE `船型` <> TRIM(`船型`) OR CHAR_LENGTH(`船型`) <> 2;
```

| 檢查 | 正確答案 | 不是這個數字代表什麼 |
|---|---|---|
| 1 孤兒筆數 | 0 | 有靠泊紀錄指向不存在的船。若測試四的 999 那筆被收下了，這裡就會回 1，而明細用 `SELECT v.voyage_id, v.ship_id FROM voyages v LEFT JOIN ships s ON v.ship_id = s.ship_id WHERE s.ship_id IS NULL;` 查得出來 |
| 2 重複的編號個數 | 0 | 主鍵失效，見測試一 |
| 3 有空格的筆數 | 0 | 非空約束失效或匯入掉格，見測試二 |
| 4 不合規筆數 | 0 | 值域沒人管。資料庫的型別只保證是數字，不保證數字合理；「船型只能是三種」這條規則目前沒有任何約束在守，只靠這句查詢 |
| 5 字元有問題的筆數 | 0 | 有肉眼看不到的差異。注意這裡要用 `CHAR_LENGTH` 算字數，`LENGTH` 算的是位元組，一個中文字在 utf8 編碼下佔 3 個位元組，用 `LENGTH` 會回 6 而不是 2，判斷式就會全部誤報 |

檢查 5 的實例在今天的教科書投影片裡就有。Ch12 第 26 頁的範例資料把「新北市」打成「新北巿」，
第二個字是巾部的「巿」不是「市」，我逐字元掃過整份 55 頁投影片，錯的那個字出現 4 次、
正確的「市」出現 0 次。所以你在 phpMyAdmin 照著文字打「新北市」去查，會回 0 筆，然後你會以為
自己 SQL 寫錯。這不是語法問題，是資料品質問題，而且只有用檢查 5 這類查詢才抓得到。

另外提醒一件會浪費你十分鐘的事：不要從教科書的 PDF 直接複製 SQL 貼到 phpMyAdmin。
投影片裡有 7 處中文彎引號混在字串裡，其中第 19、22、29 頁就在今天的授課範圍內。
彎引號不是合法的 SQL 引號，錯誤訊息也不會告訴你問題在引號。自己打直引號。

## 步驟 6　清理，2 分鐘

```sql
DROP TABLE voyages;
SELECT COUNT(*) FROM ships;            -- 必須是 50
SELECT COUNT(*) FROM ships WHERE ship_id BETWEEN 101 AND 104;   -- 必須是 0
DROP TABLE ships_backup;               -- 確認上面兩句都對了再刪
```

備份表是最後才刪。前兩句沒回到 50 與 0 就先不要刪備份，先把資料補回來。
