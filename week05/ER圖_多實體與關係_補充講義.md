# 第 5 週補充講義｜ER 圖（2/2）：兩個實體、外鍵、最小基數

> 課號 3086　2026/10/08（四）2-4 節　旗 306 海資電腦教室
> 承接第 3 週講義「ER 圖怎麼畫」。第 3 週那一節最後一句寫的是
> 「M:N 不能直接建表，一定要拆成中介實體，變成兩個 1:N。**這是下週 SQL JOIN 的前置**」。
> 今天就是那個下週。

## 零、今天只加一個新東西

第 3 週的講義已經教過：四個符號（矩形、橢圓、底線、菱形）、1:1／1:N／M:N 三種基數、
主鍵的兩個條件（不重複、不為空）、ER 圖轉資料表、`FOREIGN KEY ... REFERENCES` 的寫法。
這些今天不重講，有忘記的翻第 3 週講義第二節。

今天只加一個新東西：**最小基數**。也就是把「1:N」寫得更精確——
那個「1」端的資料，到底是「至少一筆」還是「可以零筆」。

這一個符號，就是今天下午 AI 反例 A 的答案。不標它，你看不出 AI 錯在哪裡。

## 一、為什麼今天要再看 ER 圖

今天的新語法是 `JOIN`。`JOIN` 要寫一個 `ON`：

```sql
SELECT ... FROM ships JOIN voyages ON ships.ship_id = voyages.ship_id
```

`ON` 後面那兩個欄位是哪來的？**是 ER 圖的關係線來的。**
關係線連哪兩個實體、外鍵放在哪一端，就決定了 `ON` 寫哪兩欄。
沒有 ER 圖就寫 `JOIN`，等於在猜兩張表靠什麼對起來。

所以順序是：**先有 ER 圖，才有 `JOIN`**。不是先會 `JOIN` 再回頭補 ER 圖。

## 二、你手上的 50 筆，其實是一張攤平的表

你的 `ships` 表長這樣：

| ship_id | 船型 | 噸位_千噸 | 靠泊時間_小時 |
|---|---|---|---|
| 1 | 貨櫃 | 85.3 | 18.5 |
| 2 | 散裝 | 42.1 | 26.0 |

看出問題了嗎？**一艘船只記了一次靠泊。**

真實的港口不是這樣。同一艘船這個月進來三次，每一次的靠泊時間都不一樣。
現在的設計把「船」和「這一次靠泊」擠在同一列，所以：

| 想做的事 | 現在的表做不到的原因 |
|---|---|
| 記第二次靠泊 | 只有一個「靠泊時間」欄位，第二次要塞哪裡 |
| 查這艘船今年總共靠了幾次 | 一列就是一次，數出來永遠是 1 |
| 改噸位 | 如果為了記多次而複製成多列，改噸位要改好幾列，漏一列就不一致 |

最後那一項你第 4 週作業做過，它叫**更新異常**。
解法就是第 4 週學的：**拆表**。拆成兩個實體。

## 三、兩個實體怎麼拆

| 實體 | 它代表什麼 | 屬性 | 主鍵 |
|---|---|---|---|
| **Ship 船** | 一艘船這個「東西」本身 | 船型、噸位_千噸 | `ship_id` |
| **Voyage 靠泊** | 這艘船的某一次進港靠泊 | 靠泊時間_小時、（真實系統還會有進港日期） | `voyage_id` |

判準很簡單：**屬性會不會隨著「這一次」而變。**
噸位不會——這艘船就是這麼大，進來十次都一樣，所以噸位屬於 Ship。
靠泊時間會——這次 18 小時，下次 26 小時，所以靠泊時間屬於 Voyage。

### 關係線與外鍵

```
 ┌──────────┐                        ┌──────────────┐
 │  Ship    │                        │  Voyage      │
 │ ship_id  │ PK      ◇ 靠泊 ◇       │ voyage_id    │ PK
 │ 船型      │ ──────────────────────│ ship_id      │ FK → Ship.ship_id
 │ 噸位      │   (0,N)        (1,1)   │ 靠泊時間      │
 └──────────┘                        └──────────────┘
```

**外鍵放在哪一端？** 放在「多」的那一端。
1:N 的關係，把「1」端的主鍵複製到「N」端當外鍵。
所以 `ship_id` 出現在 Voyage 裡，不是 `voyage_id` 出現在 Ship 裡。

為什麼不能反過來？因為一艘船有很多次靠泊，你沒辦法在 Ship 的一個欄位裡塞三個 voyage_id——
那會違反第 4 週學的 1NF「一格一值」。

## 四、新東西：最小基數

第 3 週你學的 `1:N` 只講了**最多**幾筆。它沒講**最少**幾筆。
完整的寫法是一對括號 `(最少, 最多)`，標在關係線的**兩端**：

| 這一端 | 記法 | 讀法 |
|---|---|---|
| Ship 這一端 | **(0, N)** | 一艘船可以有 **0 次**、1 次、或很多次靠泊 |
| Voyage 這一端 | **(1, 1)** | 每一筆靠泊紀錄必須屬於**剛好 1 艘**船 |

Ship 端為什麼是 0 而不是 1？因為**一艘船在系統裡登記了，但這個月還沒進港過**，
這完全合法。船籍資料先建好，靠泊紀錄後來才發生。

Voyage 端為什麼最少是 1？因為一筆靠泊紀錄不可能不屬於任何船。
這條規則有名字，叫**參照完整性 referential integrity**，
執行它的機制就是第 3 週講義寫過的 `FOREIGN KEY ... REFERENCES`。

### 這一個 0 今天會咬你兩次

**第一次，在測試主題 5。** 當你故意塞一筆 `ship_id = 999` 的靠泊紀錄進去，
資料庫會丟 **錯誤 1452**。它擋的就是 Voyage 端的 `(1,1)`——
你給了一筆不屬於任何船的靠泊紀錄。

**第二次，在 AI 反例 A。** 老師會前台示範 AI 寫的一句查詢。
AI 想算「每艘船靠泊幾次」，它寫了 `LEFT JOIN` 再 `COUNT(*)`。
結果 50 艘船裡有 **48 艘的答案是 1**，可是真正只靠泊一次的只有 **1 艘**。
AI 錯在哪？**它把 Ship 端的基數當成 (1,N)，以為每艘船至少靠泊過一次。**
真值是 (0,N)，有 47 艘從來沒進港，`COUNT(*)` 把那一列空的也算成 1。

這就是今天最重要的一句話：**ER 圖上少標一個 0，SQL 就會算出一個看起來很合理的錯答案。**
而且你用眼睛看不出來——螢幕上「1」就是「1」。

## 五、ER 圖轉成 `JOIN`：三個對應

| ER 圖上的東西 | SQL 裡變成什麼 |
|---|---|
| 一個實體（矩形） | 一張表 `CREATE TABLE` |
| 1:N 的關係線 | N 端多一個外鍵欄位，查詢時 `ON 兩邊的那一欄相等` |
| Ship 端的最小基數 0 | 要用 `LEFT JOIN` 才看得到那 47 艘；但 `COUNT(*)` 會算錯，要改 `COUNT(voyages.voyage_id)` |
| M:N（第 3 週講過） | 不能直接建表，開一張中介表，變成兩個 1:N，查詢要 `JOIN` 兩次 |

最後一列這一句話，第 3 週講義的原文是「這是下週 SQL JOIN 的前置」。現在你知道為什麼了。

## 六、三個當場可以自己檢查的點

畫完 ER 圖，對著這三句話檢查一遍。這三句是你今天作業的評分依據：

| # | 檢查 | 沒過代表 |
|---|---|---|
| 1 | 每個實體都有主鍵，而且主鍵不重複、不為空 | 回去看第 3 週講義「主鍵怎麼選」 |
| 2 | 外鍵在「多」的那一端，不是在「1」的那一端 | 反了，會違反 1NF |
| 3 | 關係線**兩端都寫了**括號，而且你能說出那個最小值為什麼是 0 或 1 | 只寫 1:N 不算完成，今天加的就是這個 |
